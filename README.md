# Nairobi Open

A one-file tournament app: group stages, court assignments, public score entry, live standings, and knockout brackets. Built for phones at the courts.

- `index.html`: the whole app.
- `supabase-schema.sql`: database schema plus all server-side rules, and the single source of truth for every `nairobi_` function. Run it in the Supabase SQL editor whenever it changes; it is idempotent and re-running it never touches your data, your PIN, or your rosters.
- `supabase-sms.sql` + `sms-function.ts`: the optional SMS add-on (see the SMS section).
- Live site: https://drewburd4.github.io/nairobi-open/ (GitHub repo: drewburd4/nairobi-open, deploys from `main`).

## Current status

**Wired to the Dispatch app's Supabase project (shared for now); two SQL files to run, and re-run `supabase-schema.sql` to pick up the latest fixes.** The free plan's project slots are used by duara and dispatch, so the tournament runs inside the dispatch project: every table and function is prefixed `nairobi_`, so nothing touches or collides with the Dispatch tables. The app has that project's URL and publishable key baked in. There is one live site for everyone, no separate demo mode.

Setup, in the **dispatch** project on supabase.com → SQL Editor:

Run all of `supabase-schema.sql`. That is the whole setup: it creates the `nairobi_` tables, all the write rules, and the 13 category events. On a first install it also generates a random admin PIN and prints it in the result of the last statement, which is the only time it is ever shown, so write it down before closing the tab. Run the file again after any update to this repo: the seed inserts are guarded with `where not exists`, so a re-run only refreshes the function definitions and leaves data, rosters, scores, and a changed PIN alone. There are deliberately no separate patch files to apply, so nothing can revert a fix by being run in the wrong order.

Then refresh the site: everyone with the link sees the same tournament and every change syncs live. Unlock Admin with the PIN the first run printed and change it to something memorable from the Admin tab. Enter the people on the Participants tab, then draw each event from there.

There is deliberately no sample-data file any more. It wiped every entrant and match to load its samples, which is one mis-click away from destroying a real roster mid-tournament, and it had drifted out of date besides. For a dry run, blank the two keys at the top of `index.html`: that gives a full offline copy with built-in sample data that cannot touch the live database.

**Forgot the PIN?** Nobody can read it back. Only a bcrypt hash is stored, and the hash is not readable through the public key, so there is no "remind me", only a reset. You own the database, so run this one line in the SQL editor with your own PIN in place of 246813:

```sql
update nairobi_tournaments set admin_pin_hash = crypt('246813', gen_salt('bf')) where id is not null;
```

The `where id is not null` is not decoration. There is only one tournament row, so it selects the same row either way, but the Supabase SQL editor runs in a safe mode that refuses any `UPDATE` without a `WHERE` clause and answers "Update requires a WHERE clause". Without it the statement never runs.

It applies immediately with no redeploy. Anyone already unlocked on a phone stays unlocked until that tab is closed, so if you are resetting because the PIN leaked, have the desk close and reopen the page.

The key in `index.html` is Supabase's publishable key, designed to be public; every write rule is enforced in the database. After the tournament, the whole thing can be removed from the shared project with the cleanup block commented out at the bottom of `supabase-schema.sql` (it only drops `nairobi_` objects). Moving to a dedicated project later is the same schema file, minus the prefix expectations in `index.html` (ask Claude).

## How it works

- **Events.** All categories (Open/Intermediate/Masters, singles/doubles/mixed) are pre-created. Each has its own groups, formats, and bracket. Events are started and paused from Admin, so a 4-day schedule is just: start today's event(s), pause or finish them, start tomorrow's. An event with a planned start time turns itself on an hour and a quarter early, so the first matches are already up when people arrive, and it will do so even while another event is still playing, since the courts are shared anyway. Untick "Start automatically" and it never starts on the clock. Instead it comes on when the courts are about to free up: once whatever is running is down to three matches left, or once nothing is running at all, and never earlier than an hour and a quarter before its own printed time. From five minutes before that time, unlocked admin phones get a bar naming what is due, counting what is still to play, and offering Start now or a hold time. A hold stops the idle-courts start but is overridden by three matches to go, because those courts are about to empty either way. Finals and the third place match do not count towards that three while "Finals and third place are played on the last day" is ticked on the Admin tab. That is how the afternoon batch is set up, so it cannot come on top of a morning that has not finished. It will not do so if the event already has a played match, so an event paused overnight is resumed by hand rather than restarting itself on day two off day one's start time. A manual Start or Pause always wins; saving a new time re-arms it. Schedule notes (e.g. "Sat 9am") show players what runs when. An event can be hidden from players, which is reversible and keeps everything, or deleted outright after typing its name to confirm. Hiding is the one to reach for mid-tournament: it takes the event off every player screen but leaves it in the Admin event switcher, where the desk can still reach it, and hidden events still offer their tick box on the Participants tab so a roster can be built before anyone sees the event.

  A third state sits past hidden: **archived**. An archived event leaves the app altogether, admin panel included, so last year's results and a finished side event stop being things to scroll past. Nothing in the app sets or clears it. It is a `settings.archived` flag set straight on the database, on purpose, so putting an event back is a considered act rather than a mis-tap at the desk:

  ```sql
  -- take one back out of the archive
  update nairobi_events set settings = settings - 'archived' where name = 'Open Doubles (Men)';
  ```
- **Participants.** The desk's roster of people, on its own tab that only appears once Admin is unlocked. One card per person: name, gender, a singles and a doubles DUPR rating, and their DUPR ID, entered once and reused. Tick the events each person is entered in; a tick box appears under each named row for every event that takes its entries from here. Ticking one adds a partner dropdown beside it, listing everyone else already ticked for that same event, so it is empty for the first person in and fills up as the roster grows. Picking someone pairs both sides at once and frees whoever either of them was previously down with, so a mis-pairing is one tap to fix rather than four edits; anyone already taken says who by. Renaming somebody follows them into every partner box pointing at them. Anyone left unmatched is listed by name rather than quietly guessed at. A singles event skips partners entirely: every ticked person is simply in, on their singles rating. This roster is the main way events get their entries: new events take theirs from here automatically, their draw block shows who is ready and draws straight from the ticks (naming anyone who would be left out first), and the typed entry boxes and CSV upload only appear on an event switched to "Use the entry boxes instead". The table itself has no read policy and no grants, so gender, ratings and DUPR IDs are only ever visible to an unlocked desk; names, events and partners reach the public Players tab through a function that publishes those three things and nothing else.
- **Players.** The public half of the roster, on a tab everyone sees whether or not Admin is unlocked. Names in alphabetical order with a search box; tap one to open it and see the events that person is entered in and, in doubles, who they are playing with. It reads through its own database function rather than the desk's, and that function returns a name, the events, and the partner, so gender, ratings and DUPR IDs stay behind the PIN even though the tab needs none; entries pointing at a hidden or archived event are dropped on the way out.
- **Offline backup.** Every phone with the page open quietly keeps a copy of the whole tournament in its own browser storage, refreshed each time another 25 matches are recorded and whenever a roster is saved. If the database is ever wiped, any of those phones can rebuild it: Admin → Export results shows what that phone holds, downloads it as JSON, and clears it. Because the copies live in browsers rather than on the server there is no way to clear them all remotely, so each snapshot carries a stamp (`BACKUP_EPOCH` in `index.html`) and one carrying an older stamp is discarded on sight. Bump that constant to retire every device's copy at once.
- **When each page goes up.** An event's schedule and standings are published **24 hours before its start time**, so people can plan a day around them. The event strip on Schedule, Standings and Bracket lists **every** event, not only the ones that are ready; the ones that are not yet up are dimmed, and tapping one answers the question people actually have: "Intermediate Doubles (Men)'s schedule will be released Wed 26 Aug, 8am". The Courts tab says "No events are currently active. This page will activate Thu 27 Aug, 8am" and keeps its own preview windows, which are about which court to stand at rather than who plays who: the opening events preview a day ahead, every later batch from 12 hours before its start, and only once the courts are nearly free. The bracket is the exception, because it depends on results rather than the clock: players are told it will be released after the group stage is finished, and the projected bracket by group position stays on the desk's side, since the seed order it assumes is a per-event choice that can still be changed. An event with no start time set waits for play to start. The trade-off is deliberate and worth knowing: a draw changed inside that last day is a change to something players have already read.
- **The start time is the only place a time is set.** Every date on screen is worked out from an event's Planned start: the release lines, the Courts tab's "will activate", the previews, the wait estimates, and the automatic start. Move an event on the Admin tab and all of them follow, with nothing else to edit and nobody to notify. The panel prints what players will see right under the field so the desk can watch it change. The schedule note is now for anything to add **beyond** the time ("finals day"); if a note still spells a time out, that part is ignored rather than shown next to a time that disagrees with it.
- **Courts.** One shared pool: every free court automatically takes the next match from the cross-event queue. Court share between running events is a blend: 35% divided evenly, 65% by how many matches each still has waiting, so a big draw finishes sooner without squeezing a small one down to a single court. No per-event court booking, nothing to reallocate, and no court ever sits idle while any running event has matches waiting. When one event runs out (pools done, bracket not confirmed yet), the other event flows onto its courts by itself. Starting two events one after the other lets the first take every court, so the panel offers to start others at the same moment and splits the courts in one go.
- **Queue.** Matches run in round order, group A first, so everyone plays match 1 before match 2 starts; knockout matches run in bracket order so both feeders of the same quarterfinal play close together. A team already on a court is never called to a second one: their next match waits and the queue takes the next eligible match instead. No-shows get postponed down the queue by an admin and stay visible in a Postponed list. Every waiting row has a "Move to…" picker listing the queue as it stands, so a place is chosen by the match it should go in front of; "Last in the queue" is one of the options. An on-court match can be swapped out ("Take off court"): the next match in line takes its court, the admin picks which one comes on, or the match is held. A held match is off court and out of the queue entirely until the desk puts it back, which is what to use when one team is ready and the other is not; held matches are listed under Held on the Courts tab.
- **Score entry.** Anyone with the link can enter a score, but only for a match that is currently on a court and has no score yet (winners report from the Courts tab). Everything else, including corrections, requires the admin PIN. Point targets, best-of formats, and the on-court rule are enforced server-side.
- **Corrections are on the record.** Every write to a score is kept: who entered it, when, and what it was before. A match whose score has been changed carries a "corrected" tag wherever it appears, and its modal lists the history ("14:32 · changed by the desk from 21-15 to 15-21"). This is public on purpose, because the desk being seen to change a score is what settles the argument, and a silent correction is what starts one.
- **Retirements.** A walkover is a no-show; a retirement is someone who started and could not finish, and they are recorded differently. Fill in the score as far as the match got, then press "Ret." next to whoever stopped. The score is stored exactly as it stood, including the game that was interrupted, because that is the score DUPR rates the match on: 11-5, 3-7 goes in as 11-5, 3-7. Only the games-won column is credited, so the opponent takes the match without a single point being invented. Unlike a walkover the points are real and count in the standings; the match is tagged "Ret." and the export names who retired. Best of 1 is the one awkward case, since a single pair of numbers has to carry both the score and the winner: it is left untouched when the opponent was already ahead, and otherwise the opponent is given the smallest score that wins rather than the full target.
- **Formats.** Per event and per stage: games to N points, best of 1, 3, or 5. Best-of matches record each game's score. New events default to group games best of 1 to 15 and knockouts best of 3 to 11. Knockout games always play win by 2, and the "Win by 2 in the group stage" tick is now on by default too; untick it for a day that has to run to the clock, and a group game then ends dead on the target even at 14-15.
- **Standings.** The USA Pickleball round robin order (rule 12.C): wins, then head to head among the tied teams, then point difference over all games, then head to head point difference. Head to head applies to a tie of any size, not just a pair, and whichever step separates the tie ranks everyone in it; teams still level restart the chain among themselves. Points scored settles most of what is left. Teams still level after all of it are flagged as tied, because nothing has actually separated them and the order shown is only alphabetical: the desk draws lots from the Admin tab, and the drawn order is recorded and used from then on. A walkover counts as a win and a loss but contributes no points, so a no-show cannot move anyone's point difference. Tap a team for its full schedule and results.
- **Knockout.** Set a bracket size (or Auto). Before the bracket exists, the Bracket tab shows a projected paper-style bracket by group position (A1 vs C2 and so on, no names), including "Best 3rd" wildcards used to fill the bracket so there are no byes; the connector lines show who the winner plays next. The bracket draws itself as soon as every group match of an event has a score, so the last result no longer sits there waiting for someone to press a button; "Confirm group stage finished" is still there to do it early or to rebuild. Either way it refuses while teams are level on every tiebreaker and only some of them qualify, until lots are drawn. Seeds are numbered either by how teams did (the best group winner is seed 1, on win percentage, then average point difference, then average points scored) or by group letter (A1 is seed 1, B1 is seed 2, then the runners-up), chosen per event on the Admin tab; either way every group winner is seeded above every runner-up, and the bracket puts seed 1 at the top, seed 2 at the bottom, seed 3 in the top of the bottom half. A name is never a tiebreaker anywhere in this app. When nothing separates teams competing for the same seed, the seeding is refused and the desk draws lots for it, the same way a group tie works. Each bracket also gets a **third place match** fed by the two beaten semifinalists; clearing or re-scoring a semifinal moves its loser accordingly, and is refused outright once third place has been played. Unplayed bracket matches have an admin "Edit teams" link for manual fixes.
- **Score sanity.** Public entries must match the format exactly: the winner lands exactly on the points target, or with "Win by 2" on, reaches it and leads by 2. Admin entries are free-form, but an off-format score asks for an explicit "save anyway" acknowledgement so typos don't slip through.
- **Export / DUPR.** Admin → "Export results" downloads a CSV per event (or all events): one row per played match, players split out of team names, one column pair per game, walkovers flagged. It is shaped to copy into DUPR's club "Import Matches via CSV" template; DUPR identifies people by DUPR ID, so collect each player's DUPR ID (or the email on their DUPR account) with the roster.

## Day-of cheat sheet (desk)

- Unlock Admin with the PIN once per device; it sticks for the session.
- Start the day's event(s) in Admin (just Start event; courts share automatically). Events with a planned start time start themselves an hour and a quarter early, unless "Start automatically" is unticked, in which case the desk gets a bar asking.
- Evening: pause the finished event. With nothing running, the Courts tab previews the next batch's courts and opening queue: the tournament's opening events a full day ahead, every later batch from 12 hours before its start. Nothing about a future event shows while play is running, and only the next batch to play previews (an afternoon event waits for the morning one to be paused).
- No-show or a late team: use a waiting row's "Move to…" picker to send it further down, or all the way to the back. Players not ready on court: open the match, "Take off court", and either bring someone else on or hold it until they turn up. Wrong score: tap the match anywhere, fix or clear it; the change is recorded and shown to everyone.
- Someone gets injured mid-match: type the score as it stood, then press "Ret." next to the team that stopped. Do not use W/O for this, that is for a no-show.
- Roster problems before play starts: the groups board in Admin. Drag a team to another group, or tap it and then tap the group; drop teams into Unallocated, dissolve a group, rename, remove or add in place, and press Save groups when it looks right. Groups lock once any match has a score, after which the team list still takes a late entrant and gives them catch-up matches.
- Fresh rosters: enter people once on the Participants tab, tick the events they are in (partners for doubles), and press Draw groups, either right there under "Entries so far" or in the event's draw block. The typed entry boxes and CSV upload still exist for a one-off list: switch the event to "Use the entry boxes instead" in its draw block. With a CSV header row the columns are matched by name, which is the only way to tell a DUPR ID from a rating.
- Pools done: the bracket appears by itself. If it does not, the Admin tab will say why, which is almost always a tie nothing broke.
- End of day or event: Admin → Export results (CSV) for DUPR or records.
- Useful trick: keep one phone or laptop at the desk open to the Courts tab; it updates live and works as the announcement board.

## SMS: "you're on court" texts (built in, off until set up)

When a match is assigned a court, every phone number saved for its two teams gets a text via Africa's Talking (~1KSh each; account app name "Pickleball Tournament", username `pickleball`). Numbers live in a private table the public API cannot read; admins manage them per team with the ☎ button in the Admin team list (07... numbers are normalized to +254). The trigger fires only on the moment a court is assigned, so re-calls after a swap text again but nothing double-sends, and there is a 20-per-minute flood guard.

One-time setup, in this order:

1. Run `supabase-sms.sql` in the dispatch project's SQL editor (after the main schema). Copy the `sms_shared_secret` it prints.
2. Supabase dashboard → Edge Functions → deploy a new function named exactly `nairobi-sms`, paste in `sms-function.ts`, and turn OFF "Verify JWT" for it (the shared secret replaces it).
3. Set the function's secrets: `AT_USERNAME` = `pickleball`, `AT_API_KEY` = the API key from the Africa's Talking dashboard (it lives only there, never in this repo), `NAIROBI_SMS_SECRET` = the secret from step 1.
4. Top up Africa's Talking airtime (M-Pesa works).
5. Switch it on in the SQL editor: `update nairobi_private set value = 'on' where key = 'sms_enabled';` (set `'off'` to pause any time).
6. Save a number for a test team (Admin → team list → ☎), then put its match on a court.

Texts come from Africa's Talking's default shared sender; a branded sender name needs slow carrier registration and isn't worth it for one event. Sandbox testing: add secret `AT_API_HOST` = `https://api.sandbox.africastalking.com` with `AT_USERNAME` = `sandbox`. Fallback if SMS is off: the Courts tab updates live on every phone and the desk announces, which is what most local tournaments do anyway.

## Development

No build step. Open `index.html` in a browser; with the keys wired in it talks to the live database. Blanking the two keys at the top of the file gives a local, offline, non-syncing copy with built-in sample data (dev convenience only). Tournament logic (grouping, round robin, standings, seeding, brackets, court assignment) lives in a marked pure-logic script block that can be unit tested in node.
